# Architecture audit — Veyra Atlas

Date: 2026-11-24

## Current architecture

- **Frontend:** Next.js 14 / React / TypeScript application in `web/`, with React Query, Zod, Tailwind, Framer Motion, and MapLibre.
- **Backend:** synchronous FastAPI application rooted at `main.py`; API routes are currently unversioned and use a small SQLite repository layer.
- **Raster handling:** `services/image_io.py` uses Rasterio only when present and otherwise Pillow. GeoTIFF handling currently reads only band 1 and downsizes every raster to a maximum side length of 512 pixels.
- **Inference:** Model 1 and Model 2 are deterministic NumPy baselines in `services/inference.py`. An experimental PyTorch Pix2Pix checkpoint is optional and disabled after its previous pilot result failed the quality gate.
- **Storage:** local files and SQLite, without file hashes, migrations, pagination, deletion, or object storage abstraction.
- **Geospatial output:** current vectorization uses connected-component bounding boxes and pixel/geographic transform arithmetic. It does not yet use rasterio polygonization, Shapely simplification, reprojection, or GeoTIFF/GPKG exports.

## Verified current strengths

- Predict and analyze API flows are operational and preserve the deterministic fallbacks.
- The UI correctly avoids placing unlocated JPG/PNG uploads on a world map; it uses a scene-aligned canvas instead.
- The app persists scenes, model layers, analysis records, and simple GeoJSON boundaries.
- A SAR-to-optical pilot training/data-preparation path exists and is explicitly gated as experimental.

## Gaps against the requested production target

1. **No trained flood ML model exists yet.** Flood segmentation is heuristic, and no Sen1Floods11 training/evaluation suite, published checkpoints, calibration result, or measured learned-model metrics exist.
2. **Raster support is incomplete.** Multi-band VV/VH reading, dB/linear detection, nodata handling, WGS84 display reprojection, and tiled inference are absent.
3. **Backend operations are synchronous.** There is no background job progress, upload limits, hashing cache, structured logging, versioned API, or batch/change-detection endpoint.
4. **Data engineering is minimal.** SQLite has no migrations/ORM and lacks deletion, filtering, pagination, duplicate detection, and model registry support.
5. **Quality tooling is absent.** There are no pytest tests, coverage reporting, Ruff/Mypy/pre-commit, Docker setup, CI, or reproducible lockfile.
6. **Frontend needs professional analysis controls.** It lacks live job stages, opacity controls, model-metric cards sourced from a registry, change detection, scene filters/export controls, and robust error/loading states.

## Risk and honesty assessment

- No model-quality metric will be added to the UI or documentation until it is generated by a saved evaluation run.
- The current pilot Pix2Pix model must remain disabled by default; its prior measured quality was insufficient for reliable SAR-to-optical output.
- The deterministic models remain required for fallback and baseline comparison.
- Local environment availability of GPU, Sen1Floods11 data, and training weights is not assumed. Code and smoke tests can be built now; real metrics require successful dataset acquisition and an evaluation run.

## Delivery sequence

1. Implement Sen1Floods11 data, flood-model training/evaluation, ONNX packaging, model registry, and smoke tests.
2. Improve SAR-to-optical data/training/evaluation while keeping strict promotion gating.
3. Upgrade raster, API, job, persistence, and geospatial processing paths.
4. Upgrade analysis UI and operational controls.
5. Add containerization, CI, tests, and complete reproducible documentation.
